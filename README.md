# sep3-c

Эталонная реализация SEP3 на языке C.

Спецификация протокола находится в репозитории
[jodzik/sep3](https://github.com/jodzik/sep3).

## Требования к C API

Реализация должна быть независима от ОС и HAL, не использовать динамическое
выделение памяти и предоставлять асинхронное ядро. Zephyr и STM32 HAL используют
отдельные нативные wrapper над этим ядром.

Основные требования:

- все функции возвращают `int` и используют `ErrorCodes` из
  `safe-c/safe_c.h`; новый код добавляется только при отсутствии подходящего;
- объект `Sep3` и необходимые для его объявления типы доступны в публичном
  `sep3.h`, остальные типы находятся в `sep3.c`;
- память для RX, TX, очередей и registry передаётся пользователем или wrapper;
- контрольная сумма пакета и payload для дедупликации вычисляются
  `crc32__ieee()` из `crc-c`; локальные реализации CRC в ядре отсутствуют;
- одновременно поддерживается одна исходящая и одна входящая подтверждаемая
  транзакция;
- обработчики endpoint регистрируются функциями API и действуют до повторной
  инициализации `Sep3`; unregister API не требуется;
- timeout исходящего `READ`/`WRITE` и timeout отложенного ответа входящего
  endpoint передаются непосредственно в соответствующие функции и не являются
  полями протокола;
- исходящий timeout отсчитывается от успешной первоначальной передачи и
  применяется к каждой повторной попытке одной транзакции;
- входящий timeout хранится отдельно для READ и WRITE handler’а endpoint;
- нулевой timeout недопустим и возвращает `ER_INVAL`;
- входящий запрос может получить ответ непосредственно из callback или позднее
  с использованием сохраняемого request token;
- указатель на входящий payload указывает в decoded RX-буфер ядра и
  действителен только во время callback;
- request token можно сохранить до отправки отложенного ответа или его timeout;
- один request token допускает только один логический ответ;
- `token_epoch` должен быть ненулевым и уникальным при каждой повторной
  инициализации того же объекта; platform wrapper отвечает за его хранение;
- ядро работает в одном execution context и не обязано быть потокобезопасным;
- рекурсивный вызов обработки принятых данных запрещён;
- callbacks приложения не вызываются из ISR; перенос обработки из ISR выполняет
  platform wrapper;
- callback транспорта может использовать UART DMA, поэтому TX-буфер остаётся
  действительным до явного уведомления о завершении передачи;
- повторная инициализация запрещена, пока транспорт владеет TX-буфером;
- блокирующие функции, semaphore, mutex, потоки и системные часы реализуются
  только platform wrapper, если они требуются.

## Конфигурация размера payload

Максимальный payload задаётся макросом `CONFIG_SEP3_MAX_PAYLOAD_SIZE`;
допустимый диапазон — `64..2046`. Если значение не задано, используется `244`.

В Zephyr значение предоставляет Kconfig-символ `SEP3_MAX_PAYLOAD_SIZE`. Вне
Zephyr конфигурация передаётся build-системой:

```sh
cmake -DSEP3_MAX_PAYLOAD_SIZE=512 ...
SEP3_MAX_PAYLOAD_SIZE=512 cmake ...
```

```make
CPPFLAGS += -DCONFIG_SEP3_MAX_PAYLOAD_SIZE=512
```

`sep3-c/CMakeLists.txt` читает CMake-опцию или переменную окружения
`SEP3_MAX_PAYLOAD_SIZE` и экспортирует `CONFIG_SEP3_MAX_PAYLOAD_SIZE` всем
зависимым целям.

Производные размеры:

- `SEP3_MAX_PACKET_SIZE = SEP3_MAX_PAYLOAD_SIZE + 8`;
- `SEP3_MAX_ENCODED_FRAME_SIZE = FRAMER7B_FRAME_SIZE(SEP3_MAX_PACKET_SIZE)`;
- `SEP3_MAX_ENCODED_BODY_SIZE = SEP3_MAX_ENCODED_FRAME_SIZE - 2`.

Значение влияет на layout `Sep3Buffers` и `Sep3TxSlot`, поэтому все translation
units ядра, wrapper-а и приложения должны компилироваться с одинаковой
конфигурацией.

## Буферы и TX-очередь

`Sep3Buffers` хранит постоянные буферы ядра:

- `rx[]` — encoded body принятого кадра; после in-place декодирования в нём же
  находится decoded пакет, из которого endpoint callback получает payload;
- `outgoing_packet[]` — сырой исходящий запрос для первоначальной отправки и
  retry;
- `incoming_answer[]` — сохранённый ответ на последний принятый запрос;
- `tx[SEP3_TX_SLOT_COUNT]` — encoded кадры, передаваемые транспорту.

Полный последний входящий запрос не хранится. Для дедупликации ядро сохраняет
`type`, `transaction_id`, `data_id`, размер пакета и CRC32 payload. Поля
заголовка и размер сравниваются точно, payload — по CRC32. Используется
CRC-32/ISO-HDLC: отражённый полином `0xEDB88320`, начальное и финальное
XOR-значение `0xFFFFFFFF`. Коллизия CRC32 может привести к тому, что запрос с
тем же `transaction_id` и отличающимся payload будет ошибочно принят за точный
повтор, и приложению будет повторно отправлен сохранённый ответ. CRC32
обнаруживает случайные отличия и не является криптографической защитой.

`SEP3_TX_SLOT_COUNT` равен `1`, поэтому ядро одновременно хранит один encoded
TX-кадр. Если слот занят, сохранённый incoming answer и временная протокольная
ошибка остаются pending и повторно ставятся в очередь из `sep3__process()` или
после `sep3__handle_transmitted()`. `sep3__write_no_answer()` возвращает
`ER_AGAIN`, когда свободный TX-слот отсутствует.

Временная протокольная ошибка не хранится отдельным пакетным буфером: ядро
сохраняет только `transaction_id`, `data_id` и код ошибки, а фиксированный
9-байтовый `PROTO_ERROR_ANSWER` восстанавливает непосредственно в TX-слоте.
`sep3__write_no_answer()` и `sep3__send_error_answer()` не используют локальные
буферы размером с максимальный пакет или payload.

## Контракт транспорта

`Sep3TransmitHandler` передаёт transport-слою закодированный кадр и идентификатор
его TX slot. Результат callback определяет владение кадром:

- `0` означает, что кадр принят асинхронным transport-слоем; указатель на кадр и
  его содержимое остаются действительными, но transport обязан считать их
  read-only;
- `ER_AGAIN` означает временную занятость; transport не получает владение
  кадром, а ядро повторит отправку позднее;
- любой другой код ошибки означает отказ; transport не получает владение
  кадром.

Для каждого кадра, принятого с результатом `0`, transport обязан ровно один раз
вызвать:

```c
int sep3__handle_transmitted(
    struct Sep3 *self,
    uint8_t slot_id,
    int result);
```

Вызов выполняется только после возврата из `Sep3TransmitHandler` и после того,
как transport гарантированно прекратил доступ к TX-буферу. `result == 0`
означает передачу полного кадра, ненулевой `result` — ошибку или неполную
передачу. До этого вызова ядро не освобождает и не переиспользует slot.

Отмена, timeout и остановка DMA относятся к platform wrapper. После успешной
отмены wrapper всё равно должен получить terminal completion от transport и
только затем вызвать `sep3__handle_transmitted()` с ошибкой. Если API transport
возвращает «передача уже не активна», terminal completion ранее принятого кадра
всё равно должен быть уже доставлен или гарантированно ожидаем. Отсутствие
terminal completion, повторный completion и обращение к буферу после completion
являются нарушением контракта; принудительно освобождать slot в этих случаях
небезопасно.

Для Zephyr Async UART terminal completion — это ровно одно событие
`UART_TX_DONE` или `UART_TX_ABORTED` после успешного `uart_tx()`. Успешный
`uart_tx_abort()` должен завершиться `UART_TX_ABORTED`; при гонке с естественным
завершением допустим `UART_TX_DONE`, но не оба события.

Для обработки timeout ядро получает монотонное время от wrapper:

```c
int sep3__process(struct Sep3 *self, uint64_t now_ms);
```

Абсолютное начало отсчёта времени не имеет значения. Значение `now_ms` не должно
уменьшаться между вызовами. 64-битное время позволяет ядру не обрабатывать
переполнение системного счётчика. Если платформа предоставляет 32-битное время,
его расширение до `uint64_t` выполняется platform wrapper.
